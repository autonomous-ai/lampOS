# Scope clarification for the queued-wait control

The exact mutation recorded in the authored continuation waits for cumulative `hand_ons.queued` to become zero after incrementing it. That counter never decrements; actual completion is tracked by comparing `done` with `queued`. The injected loop therefore demonstrates the parent watchdog detecting a stuck foreground loop. It is **not** a discriminating test of waiting for an acknowledgement or real completion, and no healthy-peer completion-counter control was run. This narrows earlier descriptions of it as waiting for background completion, including the PR's initial prose and builder status posts. The recorded mutation, original failure and restore receipts remain unchanged.

The separate `try_send` to `send` mutation remains an actual queue-admission regression, detected by the retained overflow-refusal assertion after the writer timeout. The idle fixture itself holds the real acknowledgement, requires foreground return before release and then checks the original source ID and contents. The fixture changes replace host stopwatch upper bounds with ordering/functional assertions; they do not detect every arbitrary foreground delay or establish physical response latency. Group B product-deadline checks remain unchanged. These limits answer the two nonblocking P3 observations on #3542.
