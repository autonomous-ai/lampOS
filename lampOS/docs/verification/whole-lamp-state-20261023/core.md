# #2809 persisted-state audit: six core crates

Source baseline: **`3e75cc3cbe4c544dee433fb8a81dc3b06daf688d`** (`3e75cc3cb`), inspected on 23 October 2026. Paths below are relative to `lampOS/`. Scope: Schedule, Tasks, Records, Memory, Skills and Setup only. Read-only source/test inspection; **no tests or builds run**, no device or network work. The checkout's in-progress Update changes were not audited or changed.

Terminology matters: **upgrade evidence** means the current reader opens older data; **forward-tolerance evidence** means the current reader opens an artificially extended/newer record; **rollback evidence** would mean an actual frozen previous reader opens data written by this build. The named tests below provide the first two kinds. **No frozen previous-reader source or executable test was found in these six crates.** A dated old-data fixture is not that test. A same-build reopen is a durability test, not a release-pair test.

“Keep/migrate/rebuild” below describes the component's reopen behavior. Whole-update file retention/restoration is described in update.md; where deployment behavior is cited from docs, it is explicitly marked as such.

## Corrections and next evidence to request

1. **Do not label these suites as frozen-old-reader coverage.** Preserve their exact current evidence, then add a release-pair harness with the actual previous reader's source/binary digest. Run current-write → previous-read/write → current-read, same boot and reboot, with observable data/authority outcomes. A test that edits an invented enum back to a known value does not substitute for the older binary.
2. **Qualify irreversible or degraded paths explicitly:** Memory JSONL import removes source files; unsupported schemas start fresh behind retained archives for Schedule/Tasks/Memory; daily-journal refusal disables daily work. None establishes full functionality after rollback. Unknown values must not acquire action/consent authority.
3. **Refresh the existing inventory rather than inheriting its old claims.** `docs/updates.md` identifies its table as a historical audit at `647f1ee63` (`:1600`): delivery ledger row `:1627` predates `delivery/saved.rs` nested tolerance; Tasks row `:1649` says schema 2 versus current 3; Setup reports row `:1666` says never read by Setup although `kept_share_reports` now does. Add Skills daily/on/rested/package-provenance rows. These are documentation drift, not new runtime failures.
4. **No new broad ownership claim.** Third is the documented Schedule/Tasks owner; Fourth owns Records/Memory. Skills/Setup need explicit task-level allocation; Second's #2809 audit does not assign all six implementations to Second.
