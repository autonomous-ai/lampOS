# Photo consent skill: source decision and remaining boundaries

Source audit pins Main `8219e711ad6de24a63f124ba86b985b2fcb3e8a3` and held Photo tree `8ad5e1ae9a9f6cc88927f377f77003451474ec50`. This is a proposed implementation plan for #2949 after #2856 lands. No code, gate, latency measurement, activation or READ-OK follows from this audit.

Use one validated, installable, default-on Photo data skill for its words and poll/quiet policy. Add no model function, executable step, dummy trigger or core grant; both route function lists must remain unchanged. Keep compiled ownership, privacy, pending-person and once-per-meeting mechanisms. The original-capture and strict-interval requirements remain separate holds.

Reuse the existing durable off-name state and atomic writer from Skills, plus the existing app/root management request. Removal must persist off intent before renaming/deleting the Photo folder. New product installation/round logic should preserve an absent-and-off Photo folder; explicit reinstall must not silently clear off, and the existing app on action is the deliberate enable. Older updaters may restore the folder, but a new runtime must still honor preserved off intent. Core restoration and unrelated skills stay unchanged.

Current `tools.json` already carries metadata, but its writer deletes the file when tools are empty and off changes alone do not publish a new policy. The proposed Photo policy must be independent of tools being nonempty, reflect enabled and not-stopped state, and revoke only Photo queued asks/Yes. Generic captured grants retain their current behavior. A previously admitted narrow No may finish deleting its one resolved pending record; it gains no ordinary forget or successor authority.

Any future policy validity begins before opening or reading any policy/off inputs. Delayed completion, publication, file reread or cached off state cannot renew it. Final cached ask/output/Yes checks must enforce their own absolute monotonic expiry even if a refresher stalls. The proposed scan/TTL/read budgets and regression cases are design targets, not measurements.

Two acceptance boundaries remain unresolved:

- **Old consumer and rollback.** Old Voice with `LAMP_PHOTO_FACES=on` keeps its Rust ask and ignores new removal policy. A proposed skill-only value on that same switch is read as off by the old exact-on parser, with no new CLI token, socket or model function. This does not solve whole rollback restoring an old on unit or manually mismatched executables; those stay HOLD until an existing rollout/unit fence is established. New Voice with absent/unsupported skill policy must disable only Photo and keep ordinary voice usable.
- **Removal acknowledgement.** Current Cloud success means manage-helper completion plus refreshed inventory, not runtime cancellation. Its separate 5 second read/write timeouts and the helper's 4 second lock wait are not one transaction deadline. No existing consumer-ack/disable barrier was found. Durable intent is not proof that queued asks/Yes are already stopped. Effective-removal acknowledgement remains HOLD pending a bounded barrier, expiry/drain and truthful partial-intent/timeout contract; a blind sleep or timer-only success is insufficient. Already-sent bytes, heard speech and committed Eyes mutations cannot be undone.

The future PR must cover loader/package validation, empty-tool metadata, off/removal/restore/reinstall, stale/slow snapshots, queued-owner cancellation, Yes at every I/O boundary, the narrow No exception, both route censuses and the old/new pairs. Actual dispatch/native checks and authorized Mobile selfie/Yes/No measurements remain required. V1's separation of instructions and untrusted labels is reusable; direct V1 enrollment, JPEG storage and instant confirmation are not this flow.
