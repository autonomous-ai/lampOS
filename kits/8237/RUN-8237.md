# #8237 ROW on an OpenClaw lamp, from stable

#8237's scope, as the reviewer-lead ruled on #7814 (23:17, 22 Nov):
1. While OpenClaw's gateway starts, a skill run asked by voice gets "One moment, I'm getting ready." once. It comes after
   the lamp's own reply and never over it. The run's answer follows, and the line never comes after the answer.
2. With a warm gateway, nothing is said.
3. Only one approvals read is in flight at a time, with back-off after a failed read.

The fourth case, stable's lamp-tasks beside #8237's lamp-skills, is not run: unit tests cover it.

**This kit has only been mocked.** It has not run on a lamp yet. `mock/run-all.sh` runs 23 cases with stub ssh, scp,
afplay, osascript, lock and push. They cover every leg's PASS, FAIL and VOID, and stopping at put, check or the
volume with stable put back by the EXIT trap. They also cover a put-back that fails with the lock kept, a held lock,
a wrong binary sha and no start budget. The last three must each stop before any lamp body runs.

Runner: 52e6's, in the slot V2 gives. The time on the lamp is about 13 min, and at most 20.

## Prerequisites
1. The lamp is on **stable**, with no update round under way. Its engine is **openclaw**, lamp-cloud is active, the
   voice's software mute is off and the mic slide is open. `check` reads all of this and stops otherwise.
2. #8237's CI ARM64 `lamp-skills` and `lamp-tasks` are on the runner's Mac: the `Rust (lampOS) ARM64` artifact of
   head `404754e832`. You need their sha256s.
3. The env file (`KIT_ENV=<path>`) is sourced, never copied or printed:
   ```
   LAMP=<lamp name>  LAMP_HOST=<address>  LAMP_USER=<ssh user>  LAMP_SUDO_PASS=<sudo password>
   LAMP_SSH_PASS=<ssh password>          # optional (sshpass -e); leave it out to use ssh keys
   LOCK_WHO=<lock holder>  KIT_LL=<path>/lamp-lock.sh   # with no KIT_LL, no lock is taken
   PR_SKILLS_BIN=<path>  PR_TASKS_BIN=<path>  PR_SKILLS_SHA=<sha256>  PR_TASKS_SHA=<sha256>
   LAMP_PAIRED=<pairing name>            # only when the Mac has more than one pairing
   ```
4. On the Mac you need bash, python3, ffmpeg, ffprobe, afplay and osascript, plus sshpass if you use LAMP_SSH_PASS.
   You also need the lampos SDK (`pip install lampOS/sdk/python`), with the Mac paired to the lamp with the `skills`
   grant (`lamp pair CODE --pin PIN --host <address>`, once).
5. The Mac's output volume must be 70 or lower. The kit only reads it, never sets any volume, and plays clips with
   `afplay -v` gain only. Put the Mac's speaker next to the lamp.

## Commands (from `kits/8237/`)
`KIT_ENV=<env> ./run.sh` runs every step in order. To resume, name a step: `./run.sh <step>`.
`./run.sh <step> <then>` runs one step, then goes on at `<then>`. `UNTIL=<step>` stops before that step.
Run one leg again with `LEGS="G A" ./run.sh legs unpush`.

| step | what it does | ~min | go on at |
|------|--------------|------|----------|
| lock | lamp-lock try, then a renew loop every 60 s (only with KIT_LL) | 0 | `LOCK TAKEN` or `LOCK none` |
| render | renders the 2 clips (`row/clips/clips.txt`: RUN "Hey Lamp, desk hello.", YES "Yes, go ahead.") through the lamp's own ElevenLabs relay | 1 | `RENDER OK` or `RENDER nothing to do` |
| put | checks both binaries' sha256 on the Mac, then copies them. Records stable's installed sha256s, binds #8237's read-only over the installed files, holds lamp-update's apply and sets `LAMP_NAME_NEAR=off` for lamp-voice. One start each of lamp-tasks, lamp-skills and lamp-voice | 1.5 | `PUT OK` |
| check | read only: engine openclaw, no round, gateway active, both units running #8237's bytes, mute off, mic slide open | 0.2 | `READY` |
| push | pushes the `row/fixtures/desk-hello` test skill from the paired Mac (`row/push.py`) | 0.5 | `PUSHED` |
| legs | `row/row.sh P G A W` | 8-9 | `VERDICT PASS` |
| unpush | removes the pushed skill from the Mac | 0.3 | `REMOVED` |
| putback | unbinds and removes the hold and the drop-in, then starts the units on stable. Proves each installed file and each running exe sha256 equals stable's, as recorded before any change | 1.5 | `PUTBACK OK` |
| release | releases the lock (needs `PUTBACK OK` and `REMOVED`) | 0 | `LOCK RELEASED` |

## The legs (`row/logs/row.txt`)
- **P**, the fixture's yes, with a warm gateway. RUN is played, then YES 12 s later (`YESAFTER=`), for the read-back
  the voice asks of a pushed skill. Its pass line is `CHECK (P1) a run handed over and answered`. With no answer in
  120 s, P is VOID, and so are G and W.
- **G**, a cold gateway. `lamp-openclaw-gateway` is restarted once (`row/gw.lamp.sh`), and RUN is played 10 s after.
  - `CHECK (G1)` lamp-tasks told getting ready exactly once.
  - `(G2)` lamp-skills asked the line exactly once, and its outcome is `say: spoken`.
  - `(G3)` the run's answer was read.
  - `(G4)` spoken means the line began before the answer was read, or it would have been taken back.
  - `(G5)` no re-send without the field.
  - It is VOID when the hand-over was not sent (the gateway was not ready in the run's deadline), or when nothing was
    told and the answer came (no cold start). Any other miss is a FAIL: a second line, a `dropped` or `expired`
    outcome, no answer, or a re-send.
  - **ROOM (G), by ear:** the line comes after the lamp's own reply to the ask and never over it, and nothing is said
    after the answer. Put what you heard on the ROW line.
- **A**, one approvals read in flight, from G's samples (`row/reads.lamp.sh`: the pids of `openclaw approvals get
  --gateway` every 0.5 s, `row/logs/g.reads`).
  - `CHECK (A1)` at most one read at once.
  - `(A2)` the reads seen and the gaps between them.
  - `(A3)` each gap is 3-15 s (±0.6 s of sampling) and doesn't shrink.
  - One read only is a PASS (no back-off needed). No read seen is VOID.
- **W**, a warm gateway, right after G. RUN is played. `CHECK (W1)` lamp-tasks told nothing, `(W2)` lamp-skills
  asked no line, and `(W3)` the answer was read.

## Journal lines the legs read (at #8237's head)
- `[lamp-tasks] skill task: the agent's start-up wait passed 5 s: told getting ready` (`lampOS/crates/tasks/src/skill_task.rs`)
- `lamp-skills: skill:desk-hello: do.task: told the lamp is getting ready: say: <outcome>` (`lampOS/crates/skills/src/main.rs`, `hand_over_saying_getting_ready`). The outcomes are the say service's: `spoken`, `dropped (...)`, `expired` and so on (`lampOS/crates/voice/src/say.rs`, `Outcome::line`).
- `lamp-skills: skill:desk-hello: do.task: lamp-tasks' answer carries ...`: the moment the run's answer is read (`main.rs`, `hand_task`).
- `lamp-skills: do.task: lamp-tasks is from before the getting-ready notice: handed over again without it` (`main.rs`, `hand_over_asking`).
- `tasks: ...; the hand-over is not sent` (`lampOS/crates/tasks/src/gateway.rs`).
- The approvals read is `/usr/local/bin/openclaw approvals get --gateway --json` (`gateway.rs`, `APPROVALS_READ`).

## Why a pushed fixture
No shipped skill under `lampOS/skills` carries a `do.task`, and a task step comes only from a Store, pushed or made
skill. So the kit pushes `desk-hello` (`grants = ["speak"]`, one `do.task`) from the paired Mac. That is the product's
route for a skill not made on the lamp (the developer door's `skill.push`). `unpush` takes it off again.

## Rules the kit keeps
- Stable's installed files are never written. #8237's binaries are read-only bind mounts under
  `/opt/lampOS/<part>/test-8237/`, gone at reboot. lamp-update's apply is held (`--apply off`, a /run drop-in) while
  they are on, so a round can't write over them.
- `LAMP_NAME_NEAR=off` for lamp-voice, by a /run drop-in, while the Mac's voice asks (the reviewer-lead's 23:17, and
  `lampOS/crates/msgs/src/lib.rs` `NEAR_ENVIRONMENT`). Say it on the ROW line. putback removes it.
- On ANY exit after put with no `PUTBACK OK`, the EXIT trap runs putback once. The lock renews first and the start
  budget is checked. The lock is kept until `release`.
- GATE refuses a start of lamp-skills, lamp-tasks or the gateway after 3 starts in the last 10 min (their
  StartLimitBurst is 5 in 600 s), and of any other unit after 9.
- An ssh call is tried again (at most 3 tries, 2 s apart) only when the lamp refused the login. The journal follow is
  never retried.
- It never sets any volume, never stops lamp-cloud, and only restarts the gateway once (leg G). Every change on the
  lamp is logged to `~/changes.txt`.
